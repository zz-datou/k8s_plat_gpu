## 1. 目标读者与课程结果

默认读者：

- 已有数年 Kubernetes 平台运维或 SRE 经验；
- 熟悉 Pod、Deployment、探针、调度、常见 kubectl 排障；
- 日常主要维护 Java/Spring Boot 容器化业务；
- 不熟悉 Go，容易被 receiver、指针、多返回值、closure、context 等挡住；
- 希望先读懂 Kubernetes 底层运行逻辑，再逐步迁移到 GPU 运维。

### 读者不是“Kubernetes 小白”，但要按“源码小白”教

可以默认读者已经知道：

- Pod、Deployment、ReplicaSet 大致是什么；
- 怎样查看对象、日志、Event 和探针；
- 一次 Java 应用发布在平台上大致怎样发生。

不能默认读者已经知道：

- controller 为什么反复 reconcile，而不是顺序执行脚本；
- informer、lister、cache、workqueue 分别做什么；
- `spec/status/Condition` 在源码里的权责区别；
- 异步、幂等、level-driven、最终一致、不变量等术语；
- Go 的指针、receiver、多返回值、slice、closure、context；
- 一条公式中的每个数从哪个对象字段而来。

讲解顺序必须是：

```text
先用一句不带新术语的人话给结论
  → 用 Java 现场和具体数字走一遍
  → 画出前后状态变化
  → 再告诉读者专业术语叫什么
  → 最后进入一小段真实源码验证
```

写作时遵守：

- 一个段落只推进一个新概念；一句话如果同时出现三个以上新术语，拆开重写；
- 专业词第一次出现时立即用口语解释，不能再用另一串专业词作定义；
- 少用“体现、契约、维度、收敛、解耦、抽象、语义”等名词堆叠；确需使用时先说具体是谁看了什么、改了什么；
- 公式先代入本例数字，再抽象成字母；变量表要写清来源字段；
- 每个源码组前先写“这段代码只回答什么”，源码后按“输入、判断、动作、结果”四项收束；
- 高级例外、版本旁支和精确调度细节标成“第二遍再读”，不能打断第一次主线；
- 首遍第一组 Go 源码应直接验证本章核心判断；handler 注册、informer 接线、queue 去重和复杂生命周期代码通常放二遍附录，除非它们本身就是中心问题；
- 第一次写“事件”时明确区分 watch/informer 的对象变化通知与 `kubectl get events` 看到的 Kubernetes Event 对象；
- 声称“字段没配置”“controller 收到 nil”之前，先核对 API defaulting、转换和禁用哨兵值；YAML 省略不一定等于 controller 内部字段为空；
- 状态字段不能凭名称猜成控制输入。逐项写清 desired、当前对象集合、status 汇总分别由谁读取、谁计算、谁写回；
- 不以缩短篇幅为目标；以读者能复述因果链为目标。

例如不要只写：

```text
controller 在异步系统中通过 level-driven reconcile 维护安全不变量。
```

应先写成：

```text
controller 每次醒来都重新看最新目标和当前副本数。
它按当前实现的顺序尝试安全动作；现在不能安全改，就先不动。
真正必须一直成立的是安全预算，不能把常见的 early return 写成“一轮永远只写一次”。
这种反复“重新看、重新算”的写法，专业名称叫 level-driven reconcile。
```

完成一章后，读者应能回答：

1. 谁拥有这份状态；
2. 什么事实会触发重算；
3. 当前函数必须守住什么不变量；
4. 为什么正常 no-op，而不是继续强行动作；
5. Error、拒绝、等待和补偿怎样区分；
6. 哪份现场证据能验证源码中的哪个变量；
7. 换一个输入后，源码会走哪个分支；
8. 相同模型迁移到 GPU 时什么不变、什么新增。

不以背目录、函数名、行号或插件列表作为学习结果。

## 2. 工作模式与源码深度

### Create

从一个真实可观察问题出发，先建立证据地图，再编写新章节。不要先写完整目录再寻找事故填空。

### Rewrite

先盘点旧章节的正确事实、链接、案例和用户改动，再重建结构。不得为了统一风格删除仍有教学价值的内容。

### Review

按严重程度报告问题，给出文件与紧凑位置。只在用户明确要求修改时落盘。

### 深度分级

| 深度 | 要求 | 适合内容 |
|---|---|---|
| S0 | 不读源码，只建立对象和组件概念 | 外围工具或暂不需要实现细节的主题 |
| S1 | 定位文件、类型和入口，说明责任边界 | 只需知道实现归属的主题 |
| S2 | 读主函数和关键分支，能从现场反查 | Deployment、常用状态传播等平台主线 |
| S3 | 读完整关键链，包含错误、no-op、异步和补偿 | scheduler、kubelet、DeviceManager 等底层主线 |

S3 不等于粘贴更多代码。只有影响不变量、状态所有权或故障判断的分支才值得深读。

## 3. 章节核心链路

所有章节都应保持以下顺序：

```text
生产矛盾
  -> 现实约束与错误直觉
  -> 设计选择和安全不变量
  -> 白板模型预测正确动作
  -> 固定版本源码验证
  -> 现场证据验证变量
  -> 反事实与 GPU 迁移
```

禁止倒置成：

```text
kubectl 命令
  -> 一堆输出
  -> 函数清单
  -> 最后补一句设计思想
```

一章只解决一个核心矛盾。旁支进入“二遍阅读”“旁读”或下一章。

## 4. 生产主案例契约

平台主线章节使用一个贯穿全章的 Java 案例。至少写清：

- namespace、服务名和工作负载类型；
- 与本章有关的 spec；
- 对象、status、Condition、Event 或资源快照；
- 可以手算的精确数字；
- 至少一个真正参与推理的 Java 特征，例如 Spring Boot 启动、JIT/GC 峰值、readiness、requests、优雅退出；
- 这是“教学整理/简化示意”还是生产原始证据。

场景数字必须贯穿白板计算、源码变量、证据命令和最终闭环。改变输入时标成反事实，不暗中改题。

开篇先让读者预测：

- 当前组件应该动作还是 no-op；
- 它必须保护什么；
- 哪个观测值变化后才允许下一步。

案例名称不是 Java 场景的充分条件。只把普通 Pod 改名为 `game-api`，却没有任何 JVM、探针、资源或发布事实参与推理，不算合格。

## 5. 设计思想契约

进入关键源码前回答五组问题：

| 问题 | 讲义必须给出的内容 |
|---|---|
| 为什么需要它 | 原始运维问题、并发或失败条件 |
| 为什么不使用直觉方案 | 会破坏的安全性、可恢复性或职责边界 |
| 它守住什么 | 可清楚判断真假的不变量 |
| 为什么这样分层 | 状态所有者与组件间契约 |
| 收益和代价 | 吞吐、延迟、复杂度、最终一致性或扩展性取舍 |

把表述分成三类：

- **源码事实**：固定提交中可以直接验证的控制流和数据关系；
- **官方设计事实**：由官方文档、KEP、proposal 或 API 语义支持；
- **教学推论**：基于前两者帮助读者建立模型的解释。

不要把教学推论写成 Kubernetes 作者的历史原话。历史提案只能解释当时动机，不能覆盖当前实现。

每个关键函数标题尽量是设计问题，例如“为什么先 Assume 再异步 Bind”，不要只是“阅读 `assumeAndReserve`”。

## 6. 源码基线与摘录契约

### 版本基线

章节必须记录：

- 本地源码目录；
- 完整 commit SHA；
- tag、branch 或 `git describe`；
- 生产排障应切换到目标集群版本的提醒；
- 实际完成的验证强度：静态阅读、逻辑核对、局部测试或全量测试。

源码定位以“文件 + 类型/函数”为主，行号只服务当前快照。外链固定到 commit SHA，不只链接漂移的 `master`。

官方概念、历史资料和当前固定提交源码分组列出，不混成一份参考资料。

### 摘录类型

每个 Go 代码组前明确标明一种：

1. **完整函数**：保留该函数所有业务分支；只增加中文注释。
2. **连续摘录**：来自同一连续区间，交代开始、结束和区间外旁支。
3. **非连续检查点**：从同一函数抽取多个检查点，明确不可独立复制编译。
4. **教学伪代码**：使用 `text` 代码块，不冒充 Go 源码。

禁止：

- 用孤立 `...` 代替删除内容；
- 把多个作用域拼成一个看似连续的 Go 块；
- 使用未交代来源的变量；
- 改写条件顺序后仍称“真实源码”；
- 只保留成功路径，删除会改变结论的 error、no-op 或 rollback；
- 把版本新增分支描述成跨版本不变行为。

真实 variadic 展开如 `failureReasons...` 可以保留，但必须当场解释它不是省略占位符。

### 源码阅读约定

第一段源码前声明：

- 中文 `//` 是讲义新增，不是上游原注释；
- 每条有控制或业务含义的语句都会解释；
- 多行调用只解释一次；
- 单独括号不机械写“括号结束”；
- 省略内容会在代码块前说明。

## 7. 中文注释与 Go 补课契约

### 应当注释

- receiver、参数和返回位置；
- 状态来自 spec、status、cache、snapshot 还是 API；
- 分支条件为什么成立；
- early return 终止了哪些后续动作；
- no-op、Error、Rejected、Wait 的语义；
- 外部调用改变了哪份状态；
- 锁、queue、goroutine、channel、context 的控制边界；
- 失败后怎样清理、重试或补偿。

### 不要机械注释

- “进入 if”；
- “定义变量”却不说变量代表什么；
- “调用函数”却不说它读写什么；
- “括号结束”；
- 与当前因果链无关的 Go 语言百科。

### 每个逻辑源码组后的收束

1. **大白话总结**：优先用四行写清“输入是什么、判断什么、改了什么、最后怎样”；再说明不能证明的内容。
2. **顺手学 Go**：只解释这段中影响理解的语法。
3. 根据需要补人话伪代码、变量表、分支表或本例手算。
4. 回扣生产现象：这段源码解释了什么，仍缺哪份证据。

逐句注释回答“这一行做什么”；大白话总结回答“整段为什么这样设计”。二者不能互相替代。

### Go 初学者规则

- 在语法第一次阻挡当前调用链时就地解释，不要求先学完整本 Go 教程；
- receiver 可暂时类比 Java `this`，但指出 Go 没有 Java class/继承语义；
- 按返回位置解释 `nil`、`false`、`0`，不要统一翻译成失败；
- 解释 `:=` 的作用域、短路、指针、slice、多返回值、类型断言、closure、`defer`、goroutine、context 等实际出现的内容；
- 章末提供快速语法索引，正文不再复制一套完整 Go 课程。

### 图表规则

- 每张图前写明从左往右、从上往下还是按时序阅读；
- 每张图说明方框、菱形、实线、虚线和箭头文字分别代表什么；
- 状态变化优先画“变化前 → 触发事实/动作 → 变化后”，并放入本例数字；
- 因果权衡表默认逐行从左往右读；如果纵向代表时间，必须明确说明；
- 一张图只回答一个问题，不能把组件拓扑、时间顺序、源码调用和业务流量全塞进同一张图；
- 异步 watch/informer 传播不能画成组件之间的同步 RPC。

## 8. 运维证据与命令契约

命令放在设计推导和核心源码之后。先写待验证变量，再选择命令。

每组证据说明：

| 内容 | 必答问题 |
|---|---|
| 观察字段 | 具体看 spec/status/Condition/Event/日志/指标的哪里 |
| 能证明 | 哪个对象事实或控制分支得到支持 |
| 不能证明 | 哪个更强的结论仍需其他证据 |
| 时间边界 | cache、API、scheduler、controller 或 kubelet 是否可能暂时不同步 |
| 操作风险 | 是否只读，是否改变现场 |

优先提供只读证据。pause、undo、删 Pod、调副本、改策略等有状态操作放入独立处置段，并写明前提、风险与回退。

禁止单证据过度推断：

- `Running` 不等于业务可服务；
- `Ready=True` 不一定等于 Deployment Available；
- `NODE=<none>` 只说明 API 中 `spec.nodeName` 尚未持久化；
- 一条 Event 不等于完整根因；
- 实时利用率低不等于 request 账本有余量；
- FitError 不等于 scheduler 进程崩溃。

Event 文本是版本相关表现，不当作稳定 API。

## 9. Java 主线与 GPU 映射

### 平台主线章节

先闭合 Java 案例。GPU 部分通常只占约 2%～5%，用一张映射表和少量边界即可：

1. 哪条不变量和控制流保持不变；
2. CPU/memory、readiness 或发布事实替换成了哪个 GPU 维度；
3. 新增了哪本设备、显存、健康或拓扑账；
4. 责任边界移到 Device Plugin、DeviceManager、driver、runtime 还是应用；
5. 哪个问题留给后续 GPU 专章。

不要在平台章节重讲第二遍相同源码，也不要提前铺开 Driver、CUDA、Container Toolkit、Device Plugin、DeviceManager 和具体 UUID 分配。

### GPU 专章

允许直接以 GPU 生产现场为主。仍要连接已经学过的 Kubernetes 模型，例如：

- extended resource 如何进入 scheduler request 账本；
- Device Plugin 状态如何进入 Node Capacity/Allocatable；
- kubelet DeviceManager 怎样在容器启动链中注入设备；
- PodResources、checkpoint 和健康变化怎样形成运维证据。

GPU 是增量专业化，不把平台 Kubernetes 能力清零重学。

## 10. 章节收束与验收

章末至少包含：

- 端到端因果链；
- 正常 no-op、业务拒绝、内部 Error 和补偿的对照；
- 必须深读、首遍略读、后续再学的边界；
- 反事实题或验收题；
- 折叠答案或可明确判断的通过标准；
- 当前版本源码断点；
- 官方概念、历史设计、固定提交源码三类参考资料；
- 下一章承接点。

首遍验收和二遍加深必须分开。标成第二遍的 queue 去重、cache 时差、定时重算、首次创建例外等内容，不得成为进入下一课的门槛。

跨函数出现 `bool`、`error`、`nil` 时，补一张最短返回值传播卡：

```text
helper 返回什么
  → caller 保留或转换成什么
  → worker 最终能看见什么
  → 谁根据 error 决定重试
```

不能把内层 helper 的 `false` 写成 workqueue 能直接看见的返回值。
也不能只画理想传播路线：固定提交中若存在 `error → false, nil`、
Status reason 转换或错误吞掉路径，必须单独画出并说明 worker 最终看不见什么。

常见路径不是不变量。首次 Create、恢复、补偿或版本新增旁支如果会让
同一轮继续执行后续判断，正文必须把“普遍底线”和“常见执行节奏”
分开写。

每个附录都要标明“首遍跳过”“只作查表”或“二遍深读”。Go 索引分成“首遍必会”和“遇到再查”；命令附录仍要先列变量和字段，再列命令。

验收题要求改变一个输入并预测分支，或要求解释“它能证明什么、不能证明什么”。不要只问函数名和字段定义。

## 11. 人工终审评分表

### MUST：任一失败都不能标记已校验

- [ ] 核心源码路径、符号、变量和分支与固定提交一致。
- [ ] API defaulting、禁用哨兵值、desired/observed 字段来源与控制输入已经核对。
- [ ] 完整函数、连续摘录和非连续检查点标注真实。
- [ ] 关键失败、no-op、等待、重试或补偿分支没有被误删。
- [ ] error 的每次上抛、转换或吞掉都按固定提交追到 worker 可见边界。
- [ ] 可见变量的来源和作用域对 Go 初学者清楚。
- [ ] 中心命题、设计问题和不变量能够解释源码判断。
- [ ] Java 主案例有精确数据且真正参与推理。
- [ ] 命令位于模型之后，并按变量和证据边界组织。
- [ ] 事实、源码解释和教学推论没有混写。
- [ ] GPU 没有抢走平台主线；GPU 专章没有退化成平台重复课。
- [ ] 没有声称运行未运行的测试。

### SHOULD：影响质量但可带说明交付

- [ ] 有一张最小调用链、不变量表或状态契约表。
- [ ] 有首遍和二遍阅读路线。
- [ ] 有反事实推演。
- [ ] 有源码断点和固定 SHA 链接。
- [ ] 相邻章节复用同一故事但不重复解释。
- [ ] 篇幅集中在当前核心矛盾，旁支有明确去向。

## 12. 常见失败模式

避免以下写法：

- 像产品说明书一样罗列插件、字段和步骤；
- 像流水账一样从文件第一行顺序念函数；
- 开篇先贴命令、日志和根因答案；
- 大段粘贴源码，却不解释为何保留该分支；
- 只讲成功路径，不讲 error、no-op、异步或补偿；
- 用“设计如此”替代证据；
- 把普通 Pod 改名成 Java 服务就声称贴近生产；
- 用 Java 类比掩盖 Go 语义差异；
- 把当前 master 行为、行号或 Event 文本写成跨版本常量；
- 把 informer 对象变化通知和 Kubernetes Event 对象混成同一种“事件”；
- 把 YAML 中省略字段直接解释成 controller 收到 `nil`，没有核对默认值；
- 把 status 汇总字段误写成 controller 创建、删除对象时的差值输入；
- 用“error 一定逐层上抛”覆盖固定提交中真实存在的 error 转换或吞掉；
- 把常见的“一次 scale 后 return”夸大成所有路径必须遵守的不变量；
- 因存在 rollback、扩容或删 Pod 命令就默认它应该执行；
- 为显得深入而堆篇幅、术语或无关函数。
- 把“有多年运维经验”误解成“已经懂 controller 理论和 Go”，直接用术语压过因果解释；
- 句子文绉绉、名词太密，读者看完仍说不出“谁看了什么、为什么没改、下一步等谁”；
- 专业词先出现很多页，后面才补大白话定义；
- 第一次阅读就要求同时掌握主线、历史旁支、cache 时差和所有边界例外。

## 13. 推荐章节骨架

```text
# 第 XX 课：Java 生产现象为什么宁愿 X，也不能 Y
> 从一次平台事故，读懂某组件的设计边界与源码主线

0. 本课定位与边界
   - 读者画像、讲什么/不讲什么、深度、首遍/二遍、中心命题

1. 当前源码基线与阅读约定
   - repo、commit、describe、生产版本提醒、摘录规则、验证强度

2. 先不执行命令：事故白板
   - 对象快照、精确数字、教学示意声明、待预测问题

3. 这个组件当初要解决什么
   - 现实约束、错误直觉、设计选择、收益和代价

4. 责任边界、状态契约与不变量

5. 源码总地图
   - 主调用链、反馈/补偿链、主读/旁读/下一章

6～N. 按“为什么”组织源码单元
   - 设计问题 -> 白板预测 -> 摘录边界 -> 注释源码
   - 大白话总结 -> 顺手学 Go -> 代入数据 -> 回扣现场

N+1. 端到端因果闭环与反事实

N+2. 现在才用命令验证
   - 按变量组织；能证明/不能证明；时间边界；操作风险

N+3. GPU 短映射或 GPU 专章承接

N+4. 哪些深读、哪些略读

N+5. 验收题、答案与通过标准

附录 A：Go 语法索引
附录 B：二遍源码断点和旁支
附录 C：值班命令与处置边界
附录 D：官方设计、历史资料、固定提交源码
```

07 类章节的设计背景、证据边界和反事实通常更重；08 类章节的范围声明、源码阅读约定和主/旁读边界通常更清晰。合并两类优点，不机械复制任一篇的编号和篇幅。
