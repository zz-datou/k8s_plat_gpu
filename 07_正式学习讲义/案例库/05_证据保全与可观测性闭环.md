# 证据保全与可观测性闭环

本篇是 B02，并把多次 controller、日志采集、ARMS 和 GPU 监控讨论整理成统一方法。

## 1. 恢复服务不等于完成事故处理

恢复后至少还要回答：

- 真正根因是否已确认，还是只有高概率推定？
- 哪个动作使服务恢复？是否可能只是同时发生的其他变化？
- 原始错误、对象状态和云资源状态是否还能复查？
- 修复是否进入 Git / 模板 / 镜像，而不是只留在现场？
- 如何检测复发？谁收到告警？

没有证据的“好了”，下一次仍然从头猜。

## 2. 四类快照

| 快照 | 内容 | 作用 |
|---|---|---|
| A：期望状态 | Git commit、render、Argo diff、发布记录 | 说明系统本来应该怎样 |
| B：Kubernetes 对象 | spec/status/condition/Event/owner/UID | 说明控制器观察到了什么 |
| C：运行时与节点 | kubelet、containerd、CNI、kernel、device | 说明 Pod 为什么无法兑现 |
| D：业务与外部系统 | 网关、LB、配置中心、数据库、日志、指标 | 说明用户为什么受影响 |

四类证据最好使用同一时间窗口、同一 context、同一 namespace、同一 Pod/Node 标识。

## 3. B02：controller 已恢复，原始错误却找不到了

### 3.1 现场

入口 504 期间，负载均衡 controller 曾重启并 BackOff。修复后新 Pod 正常，但执行 `kubectl logs --previous` 已经拿不到最早失败容器的输出。

控制面日志还能证明：旧 Pod 被删除、重建、BackOff，Deployment 被 reconcile；却看不到容器启动时的“无法获取 VPC 信息”原始错误。

这是日志责任边界，不是查询语句写错：

~~~text
EKS/ACK 控制面日志
  -> API audit、controller manager、scheduler 等托管控制面

业务/系统 Pod stdout/stderr
  -> 节点容器日志、日志 agent、Container Insights / SLS 等

云 LB 审计和状态
  -> 云 API、事件、Target Group / backend health
~~~

只开启控制面日志，不能替代工作负载容器日志。

### 3.2 还能补哪些旁证

- 旧 ReplicaSet / Pod Event 和重启时间；
- Deployment 变更前后的 args、image digest、generation；
- 云审计中 listener、target group 或 backend 变化；
- 节点仍在时的 `/var/log/pods`、`/var/log/containers`；
- 修复前后真实请求和错误率；
- 变更 commit、操作者、审批和时间。

旁证可以支持“controller 当时失效”，但不能伪装成已经拿到具体原始报错。复盘应写：`根因状态：已确认 / 推定 / 未确认`。

## 4. Kubernetes Event 不是永久日志

Event 是围绕对象状态变化的短期线索，可能被聚合、限流和过期。它不等于：

- 应用日志；
- kubelet 完整日志；
- 节点固定文件中的永久 event 日志；
- 审计日志；
- 监控时间序列。

排障时应立即保存：

~~~bash
kubectl --context <CTX> get events -A --sort-by=.metadata.creationTimestamp
kubectl --context <CTX> -n <NS> describe pod <POD>
kubectl --context <CTX> -n <NS> get pod <POD> -o yaml
kubectl --context <CTX> -n <NS> logs <POD> --all-containers --timestamps
kubectl --context <CTX> -n <NS> logs <POD> --all-containers --previous --timestamps
~~~

保存输出时要控制权限并做脱敏；ConfigMap、环境变量和日志都可能含凭据。

## 5. 时间线必须对齐

推荐统一成 UTC 或明确时区：

~~~text
T0 用户请求开始失败
T1 Pod / controller 首次异常
T2 告警触发
T3 首次人工动作
T4 关键配置修改
T5 新 Pod Ready / controller 恢复
T6 Endpoint / 云后端收敛
T7 真实请求恢复
~~~

若 T5 先于 T4，当前“修复动作导致恢复”的叙述就需要重新检查。若应用在 T5 Ready、流量到 T6 才恢复，中间窗口可能是 EndpointSlice、网关健康检查、连接排空或缓存。

## 6. 一套只读证据包

下面是模板。真实执行前先固定目标；不要把 `<CTX>` 留空后运行。

~~~bash
kubectl config current-context
kubectl --context <CTX> get ns <NS> -o jsonpath='{.metadata.uid}{"\n"}'
kubectl --context <CTX> -n <NS> get deploy,rs,pod,svc,endpointslice -o wide
kubectl --context <CTX> -n <NS> get events --sort-by=.metadata.creationTimestamp
kubectl --context <CTX> -n <NS> get deploy <APP> -o yaml
kubectl --context <CTX> -n <NS> get pod -l app=<APP> -o yaml
kubectl --context <CTX> -n <NS> logs -l app=<APP> --all-containers --since=30m --timestamps
~~~

附带保存：

~~~text
采集时间和时区
context / cluster UID / namespace UID
Git commit / Argo revision
命令版本
输出文件校验和
脱敏说明
采集失败项及原因
~~~

工具失败不能被表示成“数据为空”。例如 `grpcurl` 未安装、权限被拒或 spec 解析失败，都应单独记录。

## 7. ARMS / Agent 注入的实际验收

给 Deployment 加自动注入 label 通常只影响新创建的 Pod。只看 Deployment label 不足以证明 agent 已工作。

完整链路：

~~~text
Git patch
  -> Argo Sync
  -> Deployment pod template 变化
  -> 新 ReplicaSet / 新 Pod
  -> admission 注入 initContainer / env / volume
  -> agent 启动
  -> 监控平台收到数据
~~~

验收至少检查：

- label 位于 Pod template，而不只是 Deployment metadata；
- 是否产生新 ReplicaSet 和新 Pod；
- initContainer、环境变量、volume 是否按预期注入；
- Pod Ready、重启数和应用日志；
- 监控平台中应用名、环境和数据时间是否正确；
- 非目标运行时（例如纯 Nginx）是否被错误注入 Java agent。

“Argo 已 Synced”或“Pod 上有标签”都不是最后证据。

## 8. 凭据进入输出后的处置

聊天和诊断输出曾出现 AccessKey、Secret、token 或完整 ConfigMap 时，应按泄露处理：

1. 立即停止继续传播，不复制到讲义、Issue 或 commit。
2. 确认泄露凭据的权限、环境和有效期。
3. 轮换或吊销，优先缩短高权限凭据暴露窗口。
4. 检查终端历史、会话快照、日志系统、附件和备份的传播面。
5. 用 Secret 管理和短期身份替代明文配置。
6. 在复盘中只记录“哪类凭据曾暴露、已完成何种处置”，不记录原值。

删除一条聊天消息不能代替轮换。

## 9. GPU 监控也需要证据分层

以后看到 DCGM exporter `/metrics` 200，仍要分开：

~~~text
exporter 进程健康
  != 指标中存在目标 GPU series
  != GPU 设备健康
  != 指标正确归属到 Pod
  != 推理服务满足 SLO
~~~

GPU 实验和告警建议使用统一状态：

| 状态 | 含义 |
|---|---|
| `STATIC_REVIEWED` | 文档、YAML、规则静态审阅通过 |
| `LOCAL_EXECUTED` | 本地无集群依赖部分执行过 |
| `NO_GPU_CLUSTER_EXECUTED` | 无 GPU 集群中的 fake resource / controller 实验通过 |
| `GPU_LAB_EXECUTED` | 隔离 GPU 实验集群实际执行过 |
| `PRODUCTION_CANARY_VERIFIED` | 经过审批的生产 canary 已验证 |

每次记录 commit、镜像 digest、Kubernetes、OS、containerd、GPU/Driver、日期、原始脱敏证据、PASS/FAIL/NOT RUN 和已知限制。

## 10. 修复后的闭环

~~~text
对象恢复
  -> 真实请求恢复
  -> 指标恢复且没有隐藏错误
  -> 变更进入 Git / 模板
  -> 告警能覆盖同一故障
  -> Runbook 指向正确证据
  -> 过期的临时权限、调试资源和绕过配置已清理
~~~

## 11. 验收题

1. 为什么控制面日志不能证明 controller 容器内的具体启动错误？
2. Event、容器日志、审计日志分别回答什么？
3. ARMS 标签已进入 Deployment，为什么还不能宣布注入成功？
4. 原始日志丢失后，旁证怎样写才不会把推定冒充确认？
5. GPU 实验为什么需要区分 `STATIC_REVIEWED` 与 `GPU_LAB_EXECUTED`？
