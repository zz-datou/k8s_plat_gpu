## 1. 实验环境与安全边界

准备Python 3.9+、kubectl、kind，以及kind支持的本地容器运行环境。Windows可使用Docker Desktop的Linux容器环境或相应WSL环境；远程Linux也可以。各工具必须在执行Python的同一环境中可调用。Python 3.6不能直接使用本程序。[L1]

程序创建一套独立kind集群：一个控制面和两个worker，名称为`scheduler-study-`加随机后缀。它使用专用kubeconfig，每次kubectl显式带context和kubeconfig，并验证kube-system UID；不会使用你当前的生产context。它拒绝在任意既有生产集群上运行。

kind的多个Node仍共享同一宿主机，不代表真实物理隔离或真实多AZ。这里的CPU大request用于制造调度承诺竞争，容器本身只sleep，不做CPU压测。宿主机仍必须有足够内存、磁盘和容器运行资源。[L1]

默认容器镜像为`docker.io/library/busybox:1.37.0`，可在init用`--image`替换成公司允许的、包含sh和sleep的镜像。镜像必须实际可拉取；企业准入、安全策略与网络条件都需要现场验证。演示标签不是生产镜像安全推荐，生产使用经过安全审查的固定镜像。

## 2. 初始化与运行方式

进入本手册所在目录。先执行离线检查，不需要集群：

```bash
python3 -m py_compile scheduler_lab.py test_scheduler_lab.py
python3 -m unittest -v test_scheduler_lab
python3 scheduler_lab.py --help
```

在Windows PowerShell中可把`python3`替换为已安装的`python`，其余参数不变。

创建实验集群：

```bash
python3 scheduler_lab.py init --node-image kindest/node:v1.34.0
```

这里v1.34.0只是历史教学版本示例，不声称是当前最新版或安全补丁推荐。必须从**你所安装kind版本的官方release notes**选择兼容的版本化node image；支持填入带sha256的完整镜像引用。源码进阶的开发提交与该实验版本不同，不能把其中所有新feature gate直接搬来。[L1][L2]

程序把状态放在当前目录`.scheduler-study/`。目录包含访问该本地集群的kubeconfig，**不要上传到Git或公开分享**。本目录的`.gitignore`已忽略默认状态目录；自行更换状态目录时，也要相应保护。

执行一项实验，然后阅读现场，再清理：

```bash
python3 scheduler_lab.py run cpu
python3 scheduler_lab.py clean
```

`run`保留对象，`clean`删除本实验namespace、带专属标签的PriorityClass和实验污点，保留证据文件。不清理便运行下一项会被拒绝，以免旧实验干扰新的结论。

定制状态目录要放在子命令前，且所有命令始终一致：

```bash
python3 scheduler_lab.py --state ./my-study init --node-image kindest/node:v1.34.0
python3 scheduler_lab.py --state ./my-study run cpu
python3 scheduler_lab.py --state ./my-study clean
```

## 3. 六个自动化场景分别验证什么

| 命令中的case | 程序做什么 | 必须独立解释的结论 |
|---|---|---|
| cpu | 对同一worker先申请超过其allocatable的CPU，再创建小request对照 | 资源请求而非瞬时usage决定可行性；不能把集群总量拼给一个Pod |
| affinity | 为目标worker加专用NoSchedule污点；对比仅selector与selector+toleration | “只能去这里”和“允许进入这里”是两个条件 |
| binding | 使用故意不存在的`.invalid`镜像仓库 | nodeName已有值而镜像失败，说明责任已进入节点启动阶段 |
| gates | 创建带schedulingGate的Pod，确认未绑定，再删除gate | 准入准备不等同于资源不足；移除gate只是允许进入后续选点 |
| rollout | 用超过半个worker的CPU请求维持旧Ready副本，再触发surge；最后改变滚动预算 | 稳定态可运行不代表发布有余量；允许先下旧副本可能产生中断 |
| preemption | 低优先级先Ready；先测Never对照，再创建允许抢占的高优先级Pod | 排队优先与主动抢占不同；必须真的先有受害者占位 |

示例：

```bash
python3 scheduler_lab.py run affinity
python3 scheduler_lab.py clean
python3 scheduler_lab.py run binding
python3 scheduler_lab.py clean
python3 scheduler_lab.py run gates
python3 scheduler_lab.py clean
python3 scheduler_lab.py run rollout
python3 scheduler_lab.py clean
python3 scheduler_lab.py run preemption
python3 scheduler_lab.py clean
```

程序会改变隔离集群的对象，并在rollout场景**有意演示可能导致不可用的策略**。这不是生产修复建议。

### 3.1 为什么不写死4核或8核

rollout和preemption的CPU请求按目标worker allocatable的约55%计算，保证两个该规格Pod不能同时满足CPU承诺。程序先等待第一只Ready，才继续制造竞争；如果系统Pod、内存或镜像问题让第一只无法启动，它会失败并留下证据，不会伪造“抢占通过”。这个算法不是通用生产request核算器，也不推算init/sidecar的完整资源账。

### 3.2 为什么不把两个抢占Pod一起apply

一起提交时，高优先级可能先占到位置，此时根本没有发生抢占。本实验显式等待低优先级Ready，先验证Never不会主动驱逐，再删除Never对照并创建可抢占的高优先级Pod。低优先级容器带5秒preStop，便于记录退出阶段；20秒grace只是退出预算，不保证每次都等满。[L3]

nominatedNodeName的短暂状态不保证每次轮询都抓到。真正要关联的是Pod UID、旧Pod的删除/抢占证据、新Pod后续绑定以及资源账变化；不能因为没截到nomination就认定没发生抢占。

## 4. 输出怎么读

每次实验创建独立证据目录：

```text
.scheduler-study/
  state.json                 # 归属、集群UID、目标节点、镜像
  version.json               # 实际kubectl/server版本
  kubeconfig                 # 本地集群凭据，禁止提交
  evidence/<时间-case-随机后缀>/
    Pod-....json              # 实际提交的完整对象
    Deployment-....json       # 部分实验存在
    PriorityClass-....json    # 部分实验存在
    timeline.jsonl            # 每行一个带时间的现场快照
```

JSON清单是kubectl接受的完整API对象，不需要额外PyYAML依赖。程序在apply前调用server dry-run，但这只验证API接受与准入路径，不证明调度和运行一定成功。

`timeline.jsonl` 包含实验 namespace 的 Pod、Event、Deployment、目标 Node，以及目标节点跨 namespace 的已绑定 Pod（`node_pods`），用于核对系统组件和实验 Pod 的资源请求。计算时还需识别 Pod 阶段和实际生效的请求，不把终态 Pod 或简单容器求和无条件算作当前占用。观察 `spec.nodeName`、conditions、waiting reason、UID、deletionTimestamp 与 requests。[L4]

各对象读取不是原子快照。修改发布预算后也会轮询采样；每轮查询后约等待两秒，查询本身还会耗时，因此仍可能漏掉短暂的零可用副本。未采到不代表没有发生。本实验没有 Service 或 HTTP 探测，不能据此声称测出了业务中断时长。

终端输出`PASS`表示某一步断言成立；非零退出、Timeout或collection_error均应调查。只有cpu/affinity/gates部分步骤以绑定为验收，不声称应用已Ready；binding的预期结果就是镜像失败。请勿把“所有场景最终都要Running”当成统一标准。

## 5. 做完不算过关，解释清楚才算

每项提交下面六行，先写预测，再运行实验：

```text
预期：哪只Pod在哪个阶段等待？
约束：节点集合、资源形状、taint/selector等输入是什么？
证据：哪个UID、哪个时间、哪个字段支持判断？
反证：如果是另一个原因，应该看到什么不同事实？
变化：本次只改变了哪个变量，为什么它能改变结果？
风险：相同改法放到生产会伤害什么，如何回滚？
```

低优先级尚未Ready就继续、把镜像失败算成调度失败、用kubectl top代替request、忽略旧副本仍在服务、把降低可用性当成无风险修复，都不能判为合格。

## 6. 进阶实验需要额外环境，不伪装成已经一键支持

**拓扑联合约束：**使用主教材完整spread-demo清单，在独立实验namespace中核对所有worker的hostname/zone标签，再人为限制某域资源。先计算eligible domains和skew，再解释为什么拓扑允许的位置可能被资源拒绝。假zone只证明标签算法，不证明真实AZ高可用。

**卷协同：**需要具有相应topology能力的CSI与StorageClass。记录WFFC PVC→消费者Pod→候选节点→selected node→PV→mount的过程。默认kind动态供给不能被冒充为AWS EBS或阿里云云盘实验。没有驱动环境时，只完成对象和约束推演，明确尚未实测。[L5]

**GPU与DRA：**需要实际设备、驱动、插件或DRA driver。按进阶篇建立从物理库存到CUDA的证据链；不通过手工修改Node capacity伪装“有GPU”，也不把普通kind实验通过视为GPU链路通过。

**源码失败注入：**需要固定源码构建和集成测试环境。模拟Bind失败、插件Error、Reserve后回滚，观察Unreserve/Forget/唤醒。不能只用单测mock推导生产集群所有组件都恢复正常。

上述四类是明确的进阶任务，**不在本次六个自动化case中**。

## 7. 清理整个集群与异常恢复

先从state.json读取真实集群名，再显式确认：

```bash
LAB_NAME=$(python3 -c 'import json;print(json.load(open(".scheduler-study/state.json"))["name"])')
python3 scheduler_lab.py destroy --confirm "$LAB_NAME"
```

PowerShell：

```powershell
$LabState = Get-Content .scheduler-study/state.json -Raw | ConvertFrom-Json
python scheduler_lab.py destroy --confirm $LabState.name
```

destroy删除的是**整个本程序创建的kind集群**，证据文件保留。不要把别的学习项目长期放进这套集群。

如果创建中途失败、集群UID无法核验或API不可达，程序会拒绝自动清理，避免误删。state.json会尽早记录随机名称和creating阶段。先检查`kind get clusters`、本地容器与该名称的对应关系，再针对**确认归属的本地实验集群**按kind官方方法处理；不要为了绕过保护而修改UID、复制生产kubeconfig或把集群改名。[L1]
