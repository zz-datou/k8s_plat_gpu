# 入口流量故障树：404、405、413、503、504 与 CORS

本篇把 A03～A08 合并成一条入口责任链。先定位“谁返回的错误”，再修改配置。

## 1. 先画完整请求路径

一条请求可能跨过：

~~~text
浏览器 / 调用方
  -> DNS
  -> CDN / WAF / 公网负载均衡
  -> Ingress / 云原生网关 / Nginx
  -> Service
  -> EndpointSlice
  -> Pod IP : targetPort
  -> 应用路由 / 依赖
~~~

HTTP 状态码只说明“某一层给了这个响应”，不自动说明根因在哪一层。

## 2. 先做响应归属

保存同一次请求的时间、request ID、解析地址和完整响应头：

~~~bash
dig +short app.example.com
curl -vk --connect-timeout 5 https://app.example.com/path -o /dev/null
curl -skD - https://app.example.com/path -o /dev/null
~~~

观察这些线索：

| 线索 | 可能的响应者 |
|---|---|
| `server: cloudflare`、边缘缓存头 | CDN / 边缘 |
| 云网关特有 request ID、upstream time | 网关 |
| `server: nginx` | 可能是入口 Nginx，也可能是业务容器 |
| Spring Boot JSON error，且 path 已被去前缀 | 应用或应用网关 |
| Kubernetes Event / controller log | 解释配置为何没有真正下发 |

不能只凭一个 `server` 头最终定责，但它能决定下一组证据到哪里取。

## 3. 状态码速查

| 现象 | 第一批问题 | 常见责任层 |
|---|---|---|
| 404 | Host/path 是否命中？规则是否真正下发？ | CDN、LB listener、Ingress、Nginx、应用 |
| 405 | 到达的 method 还是原 method 吗？ | 重定向、网关 rewrite、应用路由 |
| 413 | 哪一层先读完整请求体？ | CDN/LB、网关、Nginx、应用框架 |
| 503 | 路由有后端吗？后端被判健康吗？ | 网关、Service、EndpointSlice |
| 504 | 已连接后端但未及时响应，还是后端名单陈旧？ | LB、Ingress、网关、应用依赖 |
| CORS | 浏览器收到的响应是否有正确 CORS 头？ | CDN 缓存、网关、应用 |

## 4. A04：外网 404，根因不是 Service 名称

### 4.1 现场

新增 HTTPS 路由后外网仍返回 404。开始时最直觉的猜测是 Service 与 Deployment 名称不一致。

只读检查却显示：

- Service selector 能匹配 Pod；
- EndpointSlice 有 Ready endpoint；
- 集群内通过 Service 可访问；
- Ingress 对象已经包含新路径；
- Ingress 状态只显示 HTTP listener，预期的 HTTPS listener 没有成功建立；
- Event 中持续出现证书引用无效。

进一步发现，负载均衡器在 Region B，而 Ingress annotation 引用的是 Region A 的证书。controller 无法把新模型下发到云负载均衡器，外网继续命中旧 listener 的默认 404。

### 4.2 证据顺序

~~~bash
kubectl --context <CTX> -n <NS> get ingress <INGRESS> -o wide
kubectl --context <CTX> -n <NS> describe ingress <INGRESS>
kubectl --context <CTX> -n <NS> get svc <SERVICE> -o yaml
kubectl --context <CTX> -n <NS> get endpointslice -l kubernetes.io/service-name=<SERVICE> -o yaml
kubectl --context <CTX> -n kube-system logs deploy/<LB_CONTROLLER> --since=30m
~~~

关键不是“对象里已经写了规则”，而是 controller 是否成功把模型兑现到云资源。

### 4.3 复发防护

- 证书、ALB、子网和安全组做地域一致性校验；
- CI 对 annotation 只校验格式不够，还要校验引用对象存在且属于目标地域；
- 发布验收同时检查 Ingress Event、listener 和真实 HTTPS 请求；
- 证书轮换不要只看 Kubernetes Apply 成功。

## 5. A05：页面 504，已有 ALB 为什么仍会坏

### 5.1 现场

ALB 已经稳定存在一段时间，页面突然 504。真正异常的是负载均衡 controller 重启后 CrashLoop：它没有显式 VPC 参数，启动时依赖实例元数据自动探测，当前节点上的元数据路径超时。

旧 ALB 仍存在，所以 DNS 和 listener 看上去都正常；但 controller 不能继续把新的 Pod IP、TargetGroupBinding 或后端健康状态同步给 ALB。已有云资源掩盖了控制器已经失去工作能力。

### 5.2 诊断模型

~~~text
入口资源存在
  != controller 正常
  != target group 是最新的
  != backend 可达
~~~

先检查：

~~~bash
kubectl --context <CTX> -n kube-system get deploy,pod -l app.kubernetes.io/name=<LB_CONTROLLER> -o wide
kubectl --context <CTX> -n kube-system logs deploy/<LB_CONTROLLER> --previous --tail=200
kubectl --context <CTX> get targetgroupbinding -A
kubectl --context <CTX> get nodes -o wide
~~~

托管控制面中不一定能看到所有组件日志。要事先确认容器日志采集、控制面日志、云审计和节点日志各自覆盖什么。

### 5.3 修复与门禁

如果官方 chart / controller 版本支持，显式配置已经核对过的 VPC ID可以去掉对元数据自动探测的启动依赖。但不能把“随便填一个 VPC ID”当修复。

验收应包括：

- controller Ready 且重启数稳定；
- 旧错误不再出现；
- Target Group 后端更新到当前 Ready endpoint；
- 实际请求不再 504；
- controller 再滚动一次后仍能启动。

## 6. A03：MSE 路由已发布，两个路径仍是 503

路由配置和路径重写全部正确，多数接口返回 200，只有两个服务返回 503。对应 Deployment 没有 Ready Pod，Service 的 EndpointSlice 为空，网关把后端标为 Unhealthy。

这类现场应明确写成：

~~~text
路由发布成功
  + 域名/证书成功
  + rewrite 成功
  + Service 注册成功
  - Ready endpoint
  = 入口 503
~~~

证据：

~~~bash
kubectl --context <CTX> -n <NS> get deploy,pod,svc
kubectl --context <CTX> -n <NS> get endpointslice -l kubernetes.io/service-name=<SERVICE> -o yaml
kubectl --context <CTX> -n <NS> describe pod <POD>
~~~

不要继续反复改 route。先解决为什么没有 Ready endpoint：0 副本、Pending、CrashLoop、readiness 失败或 selector 失配。

## 7. A06：HTTP POST 经 301 跳转后返回 405

### 7.1 现场

同一个业务接口：直接 HTTPS POST 能进入业务逻辑；从 HTTP 地址调用并自动跟随跳转后得到 405，应用响应头显示只允许 POST。

链路是：

~~~text
HTTP POST + JSON
  -> 边缘返回 301，Location 指向 HTTPS
  -> 客户端按自身规则跟随
  -> method 可能变成 GET，或 body 没有重放
  -> 应用返回 405 或 400
~~~

301/302 后怎样处理非 GET 请求存在客户端历史行为差异，不能假设所有客户端都保留 method 和 body。

### 7.2 怎样证明

~~~bash
# 不自动跟随，观察第一跳
curl -v http://api.example.com/path -H 'Content-Type: application/json' --data '{"k":"v"}'

# 直接请求最终 HTTPS
curl -v https://api.example.com/path -H 'Content-Type: application/json' --data '{"k":"v"}'

# 跟随跳转并输出每一跳
curl -vL http://api.example.com/path -H 'Content-Type: application/json' --data '{"k":"v"}'
~~~

最稳妥的调用方式是直接使用 HTTPS。若必须重定向非幂等请求，应评估 307/308，并用实际客户端验证 method、body 和认证头是否保留。

### 7.3 为什么不是 CORS

curl 的服务器侧 405 与浏览器 CORS 是两条问题线。CORS 失败通常由浏览器在读取响应前阻止页面使用它；服务端仍可能已经处理了请求。只有真实调用来自浏览器时，才继续检查 Origin、OPTIONS 和 CORS 响应头。

## 8. A07：上传接口 413，限制是多层取最小值

完整链路可能同时有限制：

~~~text
CDN / 公网 LB
  -> 云原生网关
  -> request-size 插件
  -> Nginx
  -> Spring / PHP / Node 框架
  -> 业务自身校验
~~~

有效上限是这些层中最先拒绝请求的最小值。

### 8.1 定位方法

| 证据 | 推断 |
|---|---|
| 网关完全没有访问记录 | 更前面的 CDN/LB 可能已拒绝 |
| 网关有 413，后端没有请求 | 网关参数、插件或入口 Nginx |
| 后端日志收到请求后拒绝 | 应用框架或业务限制 |
| 小文件成功、大文件在固定阈值失败 | 重点核对每层 body size 与 buffering |

示例配置不是万能答案：

~~~nginx
client_max_body_size 256m;
proxy_request_buffering off;
~~~

是否关闭 buffering、最大允许值和 reload 影响必须按当前云产品版本核对。应用侧也要给 multipart 开销留余量，并限制公网滥用、超时、临时磁盘和并发。

修复后至少测试：略小于阈值、刚好阈值、略大于阈值，并记录是谁返回了预期拒绝。

## 9. A08：OSS 已返回 CORS 头，浏览器为什么仍报错

静态 CSS 已在 OSS 配置 CORS，但浏览器仍收到没有 `Access-Control-Allow-Origin` 的响应。直接回源正常，问题来自 CDN 边缘仍缓存着配置变更前的旧对象响应。

### 9.1 证据

~~~bash
curl -skD - https://static.example.com/path/app.css \
  -H 'Origin: https://web.example.com' -o /dev/null

curl -skD - -X OPTIONS https://static.example.com/path/app.css \
  -H 'Origin: https://web.example.com' \
  -H 'Access-Control-Request-Method: GET' -o /dev/null
~~~

同时检查 `Age`、cache status、`Vary: Origin` 和 CORS 头。不同边缘节点可能处于不同缓存状态。

### 9.2 处置

- 先确认源站响应正确；
- 按精确 URL、前缀或 Hostname 清理适当范围的 CDN 缓存；
- 若按 Origin 返回不同响应，确保缓存键和 `Vary: Origin` 策略一致；
- 若在边缘统一设置 CORS 头，使用覆盖而非重复追加，避免多值冲突；
- 清缓存后验证第一次 MISS 和后续 HIT 都带正确响应头。

## 10. 浏览器直连 API，还是前端服务器代请求

浏览器 DevTools 中看到完整跨域 API URL、OPTIONS 预检和 CORS 头，通常说明浏览器执行 JavaScript 后直接调用 API：

~~~text
浏览器 -> 前端站点下载 HTML/JS
浏览器 -> API 域名直接请求
~~~

若是服务端代理，浏览器通常只看到同源 `/api/...`，由前端服务器再访问后端。

修改 hosts 后连接仍命中旧地址时，不要只看网页缓存。还要考虑 OS DNS 缓存、浏览器 DNS、HTTP/2 或 HTTP/3 连接池、代理/VPN 和安全 DNS。`nslookup` 直接问 DNS 服务器，不能单独证明 hosts 是否生效。

## 11. 一套统一排障顺序

1. 固定一个请求：时间、Host、path、method、body 大小、Origin、request ID。
2. 保存 DNS、TLS、每一跳状态码和响应头。
3. 明确当前响应是谁返回的。
4. 从入口规则走到 Service、EndpointSlice、Pod 和应用路由。
5. 检查 controller 是否成功兑现声明，而不只看 YAML 已 Apply。
6. 用反事实测试缩小范围：直连 HTTPS、绕过 CDN、集群内访问 Service、直连 Pod。
7. 只修改已经被证据指向的层。
8. 验证真实业务路径，并确认缓存、长连接和旧后端已经收敛。

## 12. 验收题

1. Ingress 对象已有规则，为什么云 ALB 仍可能返回旧 404？
2. 503 与 504 的证据重点有什么不同？
3. 为什么 curl 的 405 不能直接归因于 CORS？
4. 413 调大 Nginx 后仍失败，应怎样判断下一层？
5. OSS 回源正确但 CDN HIT 缺 CORS 头，修复和验证分别是什么？
