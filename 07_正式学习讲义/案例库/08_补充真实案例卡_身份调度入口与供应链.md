# 补充真实案例卡：身份、调度、入口与供应链

本篇收录 A11～A20。每张卡只保留最值得复用的判断，不重复前面专题中的完整原理。

## A11：HTTP 200，但承接流量的不是原工作负载

### 现场

同一集群有两套历史 namespace，Service 名称和镜像相似。切换后 Ingress、Pod、Endpoint 都健康，HTTP 也为 200，但实际后端是另一套迁入的工作负载，不是要求恢复的原对象。

### 关键误区

~~~text
可用性正确
  != 业务身份正确
~~~

### 最小证据

- 迁移前后的 Deployment UID、owner 和 generation；
- Ingress backend 所在 namespace；
- Service selector 与 EndpointSlice targetRef；
- Pod imageID、业务 banner 或版本标识；
- 原对象是否仍存在、是否只是被缩到 0。

### 防复发

切流验收同时验证“能访问”和“访问的是谁”。变更单必须写源/目标对象 UID 或其他稳定身份，不只写相似名称。

## A12：Argo self-heal 很快覆盖 Rancher 手改

### 现场

在集群管理界面修改 Deployment 后，API 接受了变更，但很快又恢复为 Git 中的值。

### 证据链

~~~text
人工 patch 时间
  -> 对象 generation 变化
  -> Argo 检测 drift
  -> selfHeal server-side apply
  -> live 字段恢复 Git 值
~~~

### 结论

Kubernetes 接受修改只说明写入成功，不说明字段会长期保留。先查 ApplicationSet 的 automated、selfHeal、prune、sync window 和 ignoreDifferences，再决定修 Git、暂停自动同步还是执行 break-glass。

## A13：DaemonSet Pending，强反亲和是主因，CPU request 饱和是次因

### 现场

两套日志采集 DaemonSet 并存，一套只在少数节点 Ready。节点实际 CPU 使用率很低，但 scheduler 同时报告 required anti-affinity 和某节点 `Insufficient cpu`。

### 关键判断

- required anti-affinity 在 Filter 阶段直接排除节点；
- scheduler 使用 request，不使用当前 `top`；
- 同一 Pod 可以同时有多个不可调度原因；
- “实际 CPU 3%”不能推翻“requests 已占满 Allocatable”。

### 证据

~~~bash
kubectl --context <CTX> -n <NS> describe pod <PENDING_POD>
kubectl --context <CTX> get node <NODE> -o yaml
kubectl --context <CTX> describe node <NODE>
kubectl --context <CTX> -n <NS> get ds <DS_A> <DS_B> -o yaml
~~~

先解决最广泛的 Filter 失败原因，再看剩余节点的 request 容量；不要用 `top` 代替 scheduler 账本。

## A14：删除旧 Pod 后，Job controller 又补建一个 Pending Pod

### 现场

一个历史清理 Job 仍处于可重试状态。只删除失败 Pod 后，Job controller 再创建新 Pod；旧镜像已无权限或不存在，新 Pod 进入 ImagePullBackOff，并触发实时 Pending 告警。

### 结论

~~~text
删除受控 Pod
  -> controller 看见期望未满足
  -> 补建 Pod
~~~

清理顺序应先识别 ownerReference，停止或删除真正的 Job/CronJob 控制源，再处理 Pod。告警还有时间窗口，资源删除后可能不会瞬间消失。

## A15：文件在上传机存在，Geo 域名却 404

### 现场

Dev/UAT 中上传服务和 Nginx 在同一台机器；Prod 拆成上传机与静态分发机，两台都使用本地磁盘。新图标只写入上传机，Geo Nginx 的 `alias` 读取自身主机上的同名目录，因此 404；旧图仍 200。

### 最快的证据

~~~text
域名 -> 实际 Nginx 主机
  -> 生效 location/alias
  -> 在该主机 stat 精确文件
  -> 与上传机的文件数量、mtime、hash 对比
~~~

`alias` 不能跨服务器读取目录。可用内网反向代理作为过渡，长期应使用对象存储、共享存储或显式资产同步。修复验收要包含新图 200、旧图 200、不存在图 404，以及 WMS/WMTS 等旁路不受影响。

## A16：去掉 CDN 后 WAF HTTPS 502，变化的不只是 DNS

### 现场

原链路由 CDN 终止 TLS，再以 HTTP 回 WAF。DNS 预演直连 WAF 后，客户端 HTTPS 正常到达 WAF，但 WAF 改用 HTTPS 回源到多证书网关；回源未携带正确 SNI，连接失败并表现为 502。

### 关键误区

~~~text
客户端一直使用 HTTPS
  != 内部每一跳协议从未变化
~~~

移除一层代理时要重画每一跳的协议、Host、SNI、证书、源 IP、X-Forwarded-For 和 ACL。验证不能只看 DNS 已指向新 CNAME。

## A17：TTL 已过，旧 CDN 仍有流量，强跳还可能形成循环

### 现场

权威 DNS 和公共递归 DNS 都返回新入口，但旧 CDN 仍持续收到少量真实请求。来源可能是长连接、客户端连接池、HTTPDNS、JVM DNS 缓存或固定入口。

同时，旧 CDN 使用 HTTP 回 WAF；若 WAF 对该请求强制跳转到同一个 HTTPS URL，客户端再次进入旧 CDN，可能形成重复跳转链。

### 结论

- TTL 约束 DNS 缓存，不会强制断开已有连接；
- 入口退役条件应观察旧链 QPS、连接和业务来源归零，而不是只等待 TTL；
- 新旧入口并行时，不要过早修改 XFF trust、源 IP ACL 或重定向策略；
- 用 request ID 和完整代理链证明剩余流量来自哪里。

## A18：网关把 Header 名转小写，旧 SDK 验签失败

### 现场

应用直连时响应头使用混合大小写，经 HTTP/2 / Envoy 类网关后变成小写。业务值没有变化，但旧 SDK 把响应头放入大小写敏感 Map，再按固定拼写取值，最终拿不到签名相关字段。

### 结论

HTTP Header 名语义上大小写不敏感，HTTP/2 还要求字段名小写。长期修复应让 SDK 使用大小写不敏感的数据结构；网关保留原始大小写只能是受协议限制的临时兼容，不应成为永久契约。

验证时对比直连与代理后的 header value，而不是把大小写变化本身当数据篡改。

## A19：Linux 镜像已经推送，Kubernetes 仍拉取失败

### 现场

历史 Windows 项目完成 Linux 测试、镜像构建和 registry push，但目标 ACK Pod 拉取时报 `insufficient_scope`。原因是目标 namespace / ServiceAccount 没有对应私有 registry 的拉取授权。

### 分账

~~~text
CI 能 push
  != registry 存在镜像以外的任何保证
  != 目标集群能 authenticate/pull
  != Pod 能启动
  != 业务能工作
~~~

临时 Pod 验证应固定 image digest，并使用目标 namespace、ServiceAccount、节点类型和 registry endpoint。Dockerfile 的 `HEALTHCHECK` 也不会自动变成 Kubernetes probe。

如果业务使用单实例 RWO PVC，还要评估 RollingUpdate 是否会因卷只能挂一个节点而卡住；某些场景需要 Recreate 或专门的状态迁移方案。

## A20：切图慢，不代表加 GPU 就会快

### 现场

GeoServer/GWC 切图慢，提出“加显卡能否解决”。证据显示当前路径由 Java ImageIO、CPU 渲染和磁盘 cache 构成，软件没有 CUDA/GPU 执行路径；另有源文件后缀与真实编码不一致导致解码异常。

### 决策顺序

~~~text
先证明瓶颈
  -> CPU / memory / IO / source format / thread
再证明软件存在 GPU 执行路径
  -> CUDA / OpenCL / vendor acceleration
再做可重复 benchmark
  -> 相同数据、相同参数、相同输出质量
最后才评估 GPU 成本
~~~

这个案例可以作为第 14 课的真实引子，但不能写成 NVIDIA 栈事故：没有部署 GPU，也没有 Driver、Device Plugin 或 CUDA 故障。

## A21：internal 域名不是访问控制

### 现场

内部网关为方便办公调试配置了 `/<service>/` 宽前缀。它不仅转发预期的 `/open/**`，也把 `/inner/**` 带到了上游。域名只在 Private DNS 中解析，但通过已知网关地址和 Host/SNI 仍可能绕过“没有公网 DNS”这层想象中的保护。

### 结论

- Private DNS 解决名字解析，不等于身份认证或路径授权；
- internal/public 是网络入口分类，不等于应用 API 的 open/inner 权限模型；
- 办公调试路由应收窄为明确的 `/<service>/open/`，配默认拒绝；
- 微服务内部调用继续走服务发现或受控内部入口，不为了调试暴露完整 service prefix；
- 用不存在的 open/inner audit path 验证请求究竟在网关拒绝，还是已经到达 upstream。

## A22：503 修完又 404，最后的 `Cannot GET /` 可能是正常

### 现场

网关最初把请求转到错误端口，连接失败并返回 503。修正端口后，prefix rewrite 因尾斜杠组合生成双斜杠，上游 API 返回 404。再次修正 rewrite 后健康检查和业务 API 为 200，但访问基础 URL 仍返回应用自己的 `Cannot GET /`。

### 结论

一次请求可以连续暴露三层问题：后端端口、URI rewrite、应用是否定义根路径。最终验收必须使用真实业务 path，不能要求没有 handler 的 `/` 也返回 200。
## 综合验收题

1. HTTP 200 为什么不能证明切到了正确 Deployment？
2. 实际 CPU 很低时，scheduler 为什么仍可报 Insufficient cpu？
3. 删除 Pending Pod 后为什么可能立刻出现新 Pod？
4. DNS 切换完成的退出标准为什么不是“等待一个 TTL”？
5. HTTP Header 大小写变化应在网关还是 SDK 长期修复？
6. 什么证据能证明一个工作负载真正适合 GPU？
