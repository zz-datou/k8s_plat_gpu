# Kubernetes 源码讲义工作流

把生产现象改写成以证据为基础、设计思想先行、源码主线清晰的课程。假定读者熟悉 Kubernetes 运维，但需要就地补足 Go 阅读能力。把 GPU 运维视为平台能力的增量扩展，不重置已有学习路线。

## 选择工作模式

- **Create**：从事故问题和当前源码编写新讲义。
- **Rewrite**：保留已有正确内容，重建结构、因果链和源码注释。
- **Review**：只报告有证据的问题与修改建议；用户没有要求改文件时不要实施修改。

严格按用户指定的文件、章节和深度工作，不顺手扩写无关课程。

## 恢复课程上下文

1. 完整读取 [references/lesson-standard.md](references/lesson-standard.md)。
2. 完整阅读目标 Markdown；按需读取同目录导航、前后课程、进度文件和深度说明。
3. 定位本地 Kubernetes 源码根目录，记录 commit、tag/describe 和工作区状态。
4. 用 `rg` 定位相关文件、类型、函数、调用者与测试，不凭旧讲义或函数名猜当前实现。
5. 用一句可证伪的问题定义本章边界；一章只保留一条主要因果链。
6. 确认本章模式：平台主线默认以 Java 事故为主、GPU 只短映射；GPU 专章才以 GPU 现场为主。

## 建立证据地图

动笔前整理：

- 生产现象和常见错误直觉；
- 状态所有者、组件权责和必须守住的不变量；
- 主调用链及关键状态的读写点；
- 异步、缓存、并发、失败和补偿边界；
- 可观察的 API 字段、Condition、Event、日志与指标；
- 已观察事实、固定版本源码事实、官方设计事实和教学推论。

优先使用“源码路径 + 符号 + commit”作为锚点。只有在当前版本核实后才写行号。不得编造路径、Event、日志、默认值或生产行为。

## 先讲设计，再讲机制

先回答：

1. Kubernetes 当初要解决什么真实运维或分布式问题；
2. 直觉方案会破坏什么；
3. 哪个组件拥有什么状态，维护什么不变量；
4. 为什么采用当前分层、异步、level-driven 或插件化设计；
5. 该设计获得什么，又付出什么代价；
6. no-op、业务拒绝、重试和内部 Error 分别意味着什么。

不要把“当前代码这样写”冒充未经证据支持的历史动机。历史原因优先使用官方文档、KEP、proposal 或固定提交记录。

## 构造章节

按主题取舍以下结构，不机械凑标题：

1. 本课定位、读者边界、首遍/二遍路径和中心命题；
2. 一个可观察、可手算、可证伪的生产现场；
3. 不看 Go 也能推导正确动作的白板模型；
4. 组件关系、状态契约、不变量和主调用链；
5. 三到七个围绕“为什么”的关键源码落点；
6. 带中文教学注释的真实源码；
7. 状态如何跨组件、缓存或多轮 reconcile 传播；
8. 回到现场，把证据映射到源码变量和分支；
9. 反事实场景或只读验证；
10. 必须深读、首遍认识和应推迟的内容；
11. 验收题、通过标准、源码断点和参考资料。

命令必须出现在设计模型和核心源码之后，并按“要验证哪个变量”组织，不按命令名称堆清单。

## 按契约摘录源码

每组源码都要：

1. 写明固定版本、文件和函数；
2. 标明完整函数、连续摘录或非连续检查点；
3. 交代省略的旁支及其不影响当前结论的原因；
4. 保持真实变量名、判断顺序、返回关系和 Status/error 分类；
5. 给每条有控制或业务意义的语句加大白话中文注释；
6. 说明可见变量来自 receiver、参数、前置语句还是已声明的省略上下文；
7. 在逻辑组末写“**大白话总结：**”；
8. 只解释本段确实出现且阻碍理解的 Go 写法，写“**顺手学 Go：**”。

禁止在 Go 代码块里用孤立的 `...` 代替被删除源码。真实 variadic 语法要当场解释。伪代码使用 `text` 代码块并明确标注；不能独立编译的摘录也要直说。不要给花括号、右括号或显然赋值机械凑注释。

## 校准读者与 GPU 篇幅

- 不重新讲 Pod、Deployment、探针、调度命令等使用基础。
- 把读者定位成“运维老手、源码小白”：Kubernetes 对象怎么用可以简略，但 controller 为什么这样算、状态怎样传播以及 Go 怎样表达，都要从零讲。
- 先用短句给人话结论和具体数字，再给专业术语；不要用一串术语解释另一个术语。
- 一段只推进一个新概念。源码前先写“这段只回答什么”，源码后按“输入、判断、动作、结果”四步收束。
- 把首遍必懂主线与二遍实现细节明确分开，不能让 cache、queue、时间重算等旁支同时压到第一次阅读中。
- 首遍第一组 Go 源码优先选择本章核心判断或公式；handler 注册、informer 接线和复杂生命周期代码通常移入二遍，除非它们就是本章主问题。
- 第一次出现“事件”时区分对象变化通知与 Kubernetes Event 对象；第一次说“字段没配置”时先核对 API defaulting，不能把 YAML 省略等同于 controller 收到 `nil`。
- 仅在 Go 语法阻断当前控制流时就地补课；Java 类比只作临时桥梁，并指出不等价处。
- 平台章节先闭合 Java 主案例，再用短小 GPU 对照说明“不变逻辑、替换维度、新增账本、责任转移”。
- 不在平台章节提前展开 Driver、CUDA、Device Plugin、DeviceManager 或 UUID 分配。
- GPU 专章允许以 GPU 现场为主，但要复用已经学过的 scheduler、kubelet 或 controller 模型。

## 审校和验证

1. 对照本地固定提交核验源码，重点检查失败分流、early return、异步边界、补偿路径、defaulting、nil/Status 语义和版本新增旁支；沿每条实际路径追踪 error 是否上抛、被转换或被吞掉，不用通用模式代替当前控制流。
2. 从本 Skill 目录运行机械检查：

   ```text
   # Java 平台主线，同时要求 Java 主案例和 GPU 短映射
   python scripts/validate_lesson.py <chapter.md> --require-java --require-gpu --strict

   # GPU 专章不强行要求 Java 主案例
   python scripts/validate_lesson.py <chapter.md> --require-gpu --strict
   ```

3. 把脚本检查和源码事实审计分开；脚本不能证明代码摘录真实。
4. 大幅重构时，在可用情况下安排两个独立审校：源码事实审校、教学与 Go 可读性审校。给审校者原始章节和源码，不泄漏预期结论。
5. 检查 Markdown 围栏、相对链接、导航状态、TODO/FIXME、乱码和 Go 块占位省略号。
6. 只有源码、教学和机械检查都通过后，才把导航状态更新为“已校验”。

## 交付

直接修改用户指定章节和必要导航，不另建解释本 Skill 的 README。最终说明修改的教学结构、核验的源码版本、检查结果、第一遍阅读建议，以及仍存在的版本差异或证据边界。

不要声称执行过没有运行的测试，也不要因章节很长就省略设计背景、失败路径或大白话收束。
